# Pacific Education — Stage 20.4 Learning, Assessment, Offline Sync and Data Integrity Implementation Specification\n\n**Status:** SPECIFICATION PREPARED — implementation and independent verification required.\n**Stage:** 20.4\n**Production approval:** NOT GRANTED.\n\n## 1. Purpose\nDefine the actual production behavior for learning progress, assessments, authoritative results, offline synchronization, conflict handling and data integrity.\n\n## 2. Server authority\nThe server is authoritative for learning progress, assessment attempts, results, marks, completion state, synchronization acceptance and conflict resolution.\nThe client may display and queue actions but cannot establish authoritative records.\n\n## 3. Learning-progress data\nEach progress record should contain:\n- progress_id;\n- learner_id;\n- lesson/activity_id;\n- curriculum_reference_id where applicable;\n- status;\n- completion timestamp;\n- progress version;\n- server timestamp;\n- created/updated timestamps.\n\nAllowed progress states should be explicitly defined, for example:\nNOT_STARTED → IN_PROGRESS → COMPLETED.\nInvalid transitions must be rejected server-side.\n\n## 4. Lesson completion\nWhen a learner completes a lesson:\n1. authenticate the account;\n2. verify learner scope;\n3. verify lesson availability;\n4. validate the operation;\n5. apply progression rules;\n6. update authoritative progress;\n7. record the server version;\n8. return authoritative state;\n9. create required audit evidence.\n\nThe client must not decide that completion occurred solely because localStorage changed.\n\n## 5. Assessment architecture\nSeparate:\n- assessment definition;\n- assessment version;\n- assessment items;\n- learner attempt;\n- submitted responses;\n- scoring rules;\n- authoritative result;\n- review/correction history.\n\nAn assessment version must remain identifiable after publication so historical results can be traced to the exact version used.\n\n## 6. Assessment submission\nServer checks:\n- authenticated identity;\n- learner authorization;\n- assessment availability;\n- assessment version;\n- attempt status;\n- allowed number of attempts;\n- valid response structure;\n- duplicate submission protection.\n\nThen the server records the authoritative submission and result according to the approved assessment rules.\n\n## 7. Marks and corrections\nAuthoritative results cannot be overwritten silently.\nAny correction must create:\n- correction reason;\n- previous result reference;\n- new result;\n- authorized actor;\n- timestamp;\n- audit event;\n- supporting evidence where required.\n\n## 8. Progression gates\nWhere Pacific Education uses progression gates such as mandatory assessments, the server must determine whether the gate is satisfied.\nClient-side values such as alphabetAssessment=Passed must never be treated as authoritative.\n\nEach gate must identify:\n- required condition;\n- relevant curriculum/lesson scope;\n- assessment version;\n- result reference;\n- decision timestamp.\n\n## 9. Offline operation\nOffline mode may queue permitted operations locally.\nEach operation must receive a unique operation_id.\n\nMinimum queue information:\n- operation_id;\n- authenticated account reference;\n- operation type;\n- resource reference;\n- client timestamp;\n- local operation version;\n- payload limited to necessary information;\n- queue state.\n\nNever store production credentials in the offline queue.\n\n## 10. Synchronization\nWhen connectivity returns:\n1. authenticate/revalidate session;\n2. submit operation;\n3. verify operation ID;\n4. authorize current resource scope;\n5. validate payload;\n6. check version/conflict;\n7. process transactionally where required;\n8. record audit event;\n9. return authoritative server state;\n10. mark the queue item accepted/rejected/conflicted.\n\n## 11. Idempotency\nRepeated submission of the same operation_id must not create duplicate authoritative actions.\nThe server must return the existing operation result or a controlled duplicate response.\n\n## 12. Conflict handling\nConflicts may occur when:\n- the same progress record changed on server and client;\n- an assessment attempt expired;\n- a relationship was revoked while offline;\n- a lesson was changed after the offline copy;\n- an account lost authorization;\n- the submitted version is obsolete.\n\nNever silently overwrite authoritative server data.\n\nConflict outcomes:\n- ACCEPTED;\n- REJECTED;\n- CONFLICT_REVIEW_REQUIRED;\n- SUPERSEDED_BY_SERVER_STATE.\n\n## 13. Authorization during sync\nPrevious offline authorization does not guarantee current authorization.\nThe server rechecks:\nidentity → account status → role → relationship → resource scope → permission.\n\nRevoked relationships must cause affected operations to be rejected where current authorization is required.\n\n## 14. Transactions and integrity\nUse database transactions for operations that must succeed or fail together.\nExamples:\n- assessment submission + result;\n- relationship activation/revocation;\n- class membership change;\n- accepted sync operation + authoritative update;\n- correction + audit event.\n\nUse foreign keys/constraints or equivalent integrity controls to prevent orphaned authoritative records.\n\n## 15. Migration controls\nEvery schema migration requires:\n- migration ID;\n- version;\n- description;\n- affected tables/domains;\n- development test;\n- staging test;\n- backup/recovery consideration;\n- reviewer;\n- deployment record;\n- rollback/recovery plan.\n\nProduction migrations must not be performed from an uncontrolled personal device or directly from an unreviewed browser action.\n\n## 16. Data validation\nValidate all server inputs for:\n- type;\n- length;\n- allowed values;\n- identifiers;\n- dates/timestamps;\n- ownership/scope;\n- version;\n- duplicate operations;\n- malicious or malformed input.\n\nNever trust client-provided role, permission, mark, completion or approval fields.\n\n## 17. API behavior\nLearning endpoints must return only the data authorized for the authenticated account.\nAssessment endpoints must prevent unauthorized access to other learners' attempts/results.\nSync endpoints must be idempotent and conflict-aware.\n\nRecommended endpoint families:\n- /api/learning/progress\n- /api/learning/lessons\n- /api/assessments\n- /api/assessment-attempts\n- /api/results\n- /api/sync\n\nActual production routes may differ, but the authorization and integrity requirements remain.\n\n## 18. Failure behavior\nIf authentication, authorization, database, payment verification or other authoritative dependency is unavailable:\n- do not fabricate success;\n- do not grant access;\n- do not create false marks;\n- do not activate entitlements;\n- preserve safe local work where appropriate;\n- report a clear recoverable status;\n- retry safely using idempotency.\n\n## 19. User-facing status\nUse clear states such as:\n- Saved to device;\n- Waiting to sync;\n- Successfully synced;\n- Needs review;\n- Rejected;\n- Conflict detected;\n- Service temporarily unavailable.\n\nDo not tell users that data is permanently saved to the production system until the server confirms it.\n\n## 20. Privacy and child-data minimization\nOffline data should be minimized and protected.\nDo not cache unnecessary learner information.\nDefine cache expiry and secure deletion.\nSensitive records must not be exposed through notifications, URLs or debug logs.\n\n## 21. Audit events\nRecord material events including:\n- progress completion;\n- assessment submission;\n- authoritative result creation;\n- result correction;\n- synchronization acceptance/rejection;\n- authorization denial where required;\n- conflict resolution;\n- relationship changes.\n\nAudit records must not contain unnecessary sensitive payloads.\n\n## 22. Required test matrix\nTest:\n1. normal online lesson completion;\n2. duplicate completion;\n3. unauthorized learner progress access;\n4. teacher outside assigned scope;\n5. parent/guardian outside verified relationship;\n6. assessment submission;\n7. duplicate assessment submission;\n8. unauthorized mark modification;\n9. correction workflow;\n10. offline completion;\n11. offline assessment queue;\n12. duplicate sync;\n13. stale sync;\n14. revoked relationship during offline period;\n15. conflicting progress;\n16. server outage;\n17. database outage;\n18. malformed input;\n19. migration rollback/recovery;\n20. restored backup consistency.\n\nExpected security result: unauthorized operations are denied and authoritative data is not corrupted.\n\n## 23. Evidence required\nStage 20.4 evidence must include:\n- implemented learning persistence;\n- implemented assessment persistence;\n- authoritative result behavior;\n- synchronization implementation;\n- conflict tests;\n- idempotency tests;\n- authorization tests;\n- migration evidence;\n- backup/recovery evidence;\n- audit verification;\n- independent technical verification.\n\nEvidence must identify environment, test date, verifier and safe reference.\n\n## 24. Completion rule\nStage 20.4 remains INCOMPLETE until practical implementation and required verification are completed.\nDocumentation alone does not satisfy the evidence requirement.\n\n## 25. Automatic transition\nWhen Stage 20.4 practical evidence is independently verified, Guardian may prepare the next controlled review package and evidence index.\nIt must not declare legal compliance, production readiness or release approval.\n\n## 26. Release boundary\nCompletion of Stage 20.4 does not authorize production launch.\nStages 20.5–20.7 and all applicable production, security, privacy, safeguarding, curriculum, payment, professional/legal and owner controls remain separate gates.\n\n**Current status: PREPARED — implementation required.**
