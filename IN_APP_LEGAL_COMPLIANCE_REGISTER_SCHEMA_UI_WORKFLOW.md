# Pacific Education — Actual In-App Legal & Compliance Register Data Schema and UI/Workflow Specification\n\n**Status:** IMPLEMENTATION SPECIFICATION — practical coding, security testing and professional/legal review remain required.\n\n## 1. Security boundary\nThe register is a protected production feature. The browser UI is untrusted. The server must be authoritative for identity, roles, permissions, register records, review status, evidence status, approval status, publication status and audit history.\n\n## 2. User roles\nOwner: governance access, owner approval and authorized publication decisions.\nLegal/professional reviewer: assigned reviews, findings and revision requests within their authority.\nCompliance/governance administrator: register maintenance, evidence coordination and review packages.\nTechnical/security reviewer: assigned technical verification only.\nEducation/curriculum reviewer: assigned curriculum-source and mapping review only.\nGeneral user: no restricted register access.\n\n## 3. Core database schema\n\n### compliance_requirements\nFields: requirement_id, requirement_code, category, title, description, jurisdiction, affected_population, applicable_status, applicability_reason, source_authority, source_title, source_reference, source_version, source_published_date, source_effective_date, source_checked_at, implementation_owner_id, affected_feature, current_status, priority, next_review_at, created_at, updated_at, created_by, updated_by.\n\n### compliance_evidence\nFields: evidence_id, requirement_id, evidence_type, title, description, safe_reference, environment, verification_status, verified_by, verified_at, expires_at, confidentiality, created_at, created_by.\nNever store passwords, private keys, access tokens, payment credentials or unnecessary child personal information.\n\n### compliance_reviews\nFields: review_id, requirement_id, document_version_id where applicable, review_type, reviewer_id, reviewer_role, review_scope, outcome, findings, required_changes, conditions, reviewed_at, follow_up_at, created_at.\n\n### compliance_approvals\nFields: approval_id, requirement_id, approval_type, approver_id, approved_version, decision, conditions, decision_at, evidence_reference, created_at.\n\n### compliance_documents\nFields: document_id, document_code, document_type, title, jurisdiction, audience, version, status, content_reference, source_reference, effective_at, published_at, superseded_at, review_due_at, access_classification, created_at, updated_at.\n\n### compliance_document_changes\nFields: change_id, document_id, from_version, to_version, change_reason, changed_sections, impact_summary, required_reviews, created_by, created_at.\n\n### publication_records\nFields: publication_id, document_id, version, publication_channel, public_location, published_at, effective_at, publication_status, accessibility_check_status, owner_approval_id, created_at.\n\n### legal_authority_decisions\nFields: authority_decision_id, requirement_id, authority_name, instrument_type, application_reference, submitted_at, decision_at, decision, conditions, expires_at, official_reference, verified_by, verified_at.\nThe system must not create an official decision record without actual supporting evidence.\n\n### compliance_tasks\nFields: task_id, requirement_id, task_type, assigned_to, due_at, status, priority, completion_evidence_id, created_at, completed_at.\n\n### compliance_issues\nFields: issue_id, requirement_id, severity, description, status, owner_id, corrective_action, due_at, resolved_at, resolution_evidence_id, created_at, updated_at.\n\n### compliance_audit_events\nFields: audit_event_id, entity_type, entity_id, action, actor_id, old_state, new_state, reason, correlation_id, created_at.\nAudit history must be append-only to ordinary users.\n\n## 4. Enumerations\nCategories: PRIVACY_DATA, CHILD_SAFEGUARDING, EDUCATION_CURRICULUM, CYBERSECURITY, ACCESSIBILITY, PAYMENT_CONSUMER, TERMS_USER_AGREEMENT, CONSENT, TEACHER_STAFF, INTELLECTUAL_PROPERTY, VENDOR_HOSTING, RETENTION_DELETION, COMPLAINTS_DISPUTES, INSURANCE_RISK, BUSINESS_TAX, APP_MARKETPLACE, INTERNATIONAL, OTHER.\nStatuses: PLANNED, IMPLEMENTED, EVIDENCE_READY, SPECIALIST_REVIEW, LEGAL_REVIEW, REVISION_REQUIRED, OWNER_APPROVAL, PUBLISH_READY, PUBLISHED, EFFECTIVE, SUPERSEDED, BLOCKED, NOT_APPLICABLE, WITHDRAWN.\n\n## 5. State-transition rules\nNormal path: PLANNED → IMPLEMENTED → EVIDENCE_READY → SPECIALIST_REVIEW → LEGAL_REVIEW → OWNER_APPROVAL → PUBLISH_READY → PUBLISHED → EFFECTIVE → SUPERSEDED.\nREVISION_REQUIRED returns to the appropriate earlier state. BLOCKED cannot advance until resolved. NOT_APPLICABLE requires recorded reasoning and authorized review. PUBLISHED requires a frozen approved version. EFFECTIVE requires publication and an effective date. The server must reject invalid transitions.\n\n## 6. Dashboard UI\nRoute: /admin/compliance\nHeader: Legal & Compliance Register\nSubtitle: Evidence, review and publication management — not a legal-compliance certification system.\nSummary cards: Total requirements, Evidence ready, Specialist review, Legal review, Owner approval, Publish ready, Effective, Blocked, Overdue.\nFilters: category, jurisdiction, status, priority, assigned reviewer, due date and publication status.\nDo not display a single compliance score or legally compliant badge.\n\n## 7. Requirement list\nColumns: Code, Title, Category, Jurisdiction, Status, Priority, Evidence, Reviewer, Next review, Blocking issue. Selecting a record opens its detail page.\n\n## 8. Requirement detail\nSections: Overview; Source; Implementation; Evidence; Reviews; Authority decisions; Approval; Publication; Issues; Audit.\nShow exact document versions and reviewer outcomes. Show government decisions only when documented.\n\n## 9. Create requirement\nNew Requirement form: category, title, description/question, jurisdiction, affected population, proposed applicability, source authority, source title/reference, source version/date, affected app feature, implementation owner, priority and next review date.\nSaving creates PLANNED. The system must not automatically decide legal applicability.\n\n## 10. Evidence workflow\nAdd Evidence requires evidence type, description, safe reference, environment, verifier and verification status. The system distinguishes SUBMITTED from VERIFIED. Only verified mandatory evidence can satisfy a requirement.\n\n## 11. Review workflow\nRequest Review selects specialist, legal/professional, technical/security, curriculum/education or another authorized review. Reviewer actions: reviewed, revision required, blocked, or additional evidence required. The exact version reviewed is recorded.\n\n## 12. Owner approval\nOnly an authorized owner can approve. Show exact version, review results, unresolved issues, conditions and evidence. Actions: Approve, Reject, Return for revision. Require explicit confirmation.\n\n## 13. Publication workflow\nPrepare Publication checks required reviews, approvals, blocking issues, document version, jurisdiction, effective date, accessibility status and authority evidence where applicable.\nIf any applicable condition fails: PUBLISH BLOCKED. If all applicable conditions pass: PUBLISH READY. Publication remains controlled.\n\n## 14. Public document page\nShow title, current version, effective date, publication date, applicable jurisdiction, accessible content and contact route. Do not expose legal advice, confidential reviewer notes, security vulnerabilities, safeguarding case information, private contracts or personal data.\n\n## 15. Automatic practical-to-legal workflow\nSTAGE VERIFIED → linked requirement/task → evidence index → professional reviewer identification → review questions → draft/update package → reviewer notification → review → revision if required → owner approval where applicable → publication gate.\nGuardian automation may prepare these records. It may not mark legal approval, invent authority approval, certify compliance, bypass review, publish confidential legal advice or authorize production release.\n\n## 16. Application feature triggers\nNew personal-data field → privacy review task.\nNew child-facing feature → safeguarding/privacy review tasks.\nNew teacher/parent communication → safeguarding/privacy/terms review.\nNew payment method → payment/consumer/privacy/reconciliation review.\nNew curriculum mapping → curriculum-source verification.\nNew jurisdiction → jurisdictional review package.\nAuthentication/authorization change → security/privacy review.\nMajor terms/privacy change → invalidate previous PUBLISH_READY and require re-review.\n\n## 17. Notifications\nAuthorized users may receive review requests, revision requests, blocked-item alerts, owner-approval requests, publication-ready alerts, overdue review alerts, source-change alerts and evidence-expiry alerts. Notifications must contain minimum necessary information.\n\n## 18. API surface\nIllustrative server endpoints:\nGET /api/admin/compliance/requirements\nPOST /api/admin/compliance/requirements\nGET /api/admin/compliance/requirements/{id}\nPATCH /api/admin/compliance/requirements/{id}\nPOST /api/admin/compliance/requirements/{id}/evidence\nPOST /api/admin/compliance/requirements/{id}/reviews\nPOST /api/admin/compliance/requirements/{id}/approvals\nPOST /api/admin/compliance/documents\nPOST /api/admin/compliance/documents/{id}/versions\nPOST /api/admin/compliance/documents/{id}/publication-check\nPOST /api/admin/compliance/documents/{id}/publish\nGET /api/admin/compliance/audit\nEvery endpoint requires server-side authentication and authorization.\n\n## 19. API authorization matrix\nOwner: authorized governance access and publication approval.\nLegal/professional reviewer: assigned review only; owner approval denied unless separately authorized.\nTechnical/security reviewer: assigned technical evidence only; legal approval denied.\nCompliance administrator: workflow records allowed; final owner approval denied.\nGeneral user: restricted register denied.\n\n## 20. Data protection controls\nImplement encryption in transit, appropriate encryption at rest, secret management outside source, least-privilege database access, audit logging, rate limiting, secure sessions, input validation, data minimization, backups/restoration and incident response.\n\n## 21. Accessibility and mobile UI\nResponsive Android/desktop layout, readable text, sufficiently large controls, clear status labels, no color-only status meaning, accessible errors, simple filters, pagination and low-bandwidth-friendly pages.\n\n## 22. Offline restriction\nLegal approval and publication actions must not be finalized offline. Final legal review decisions, owner approval, publication and effective activation require current server verification.\n\n## 23. Audit\nRecord creation, edits, status transitions, evidence verification, reviews, approvals, rejection, publication, supersession, authority-decision updates and restricted-record access where required. Record actor, timestamp, record and action.\n\n## 24. Mandatory tests\nTest unauthorized access; reviewer cannot owner-approve; missing evidence blocks advancement; unverified evidence cannot satisfy a requirement; missing professional review blocks applicable publication; unresolved blockers prevent publication; superseded documents cannot become current accidentally; version changes trigger review; false authority approvals cannot be created; Guardian cannot mark legal approval; confidential records remain restricted; audit events are generated; invalid transitions are rejected; offline clients cannot finalize approval/publication; API access cannot be bypassed by modifying IDs or role fields.\n\n## 25. Implementation evidence\nRecord database migration/version, server API implementation, authorization tests, UI tests, publication-gate tests, audit tests, accessibility/device tests, backup/recovery verification, independent technical review and unresolved defects.\n\n## 26. Production/legal boundary\nThis specification does not establish legal compliance, registration, licensing, government approval, Ministry approval, certification or legal effectiveness. Actual requirements must be determined and reviewed for the real Pacific Education service, users, jurisdictions, data flows, contracts and deployment model.\n\n**Implementation status: SPECIFICATION READY — coding and verification required.**
